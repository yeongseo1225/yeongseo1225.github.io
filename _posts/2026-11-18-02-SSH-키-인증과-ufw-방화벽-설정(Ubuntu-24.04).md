이번에는 맥에서 SSH로 서버에 접속하고, 비밀번호 대신 SSH 키로 로그인하도록 바꾼 뒤 ufw 방화벽까지 켜 보았다.

ubuntu-lab은 UTM 공유 네트워크 안에 있어서 실제로는 내 맥에서만 닿는 서버다. 그래도 인터넷에 열린 실제 서버라면 비밀번호만 알면 누구든 접속을 시도할 수 있고, 방화벽도 따로 없는 상태다. 그 상황을 가정하고 연습했다.

## SSH 란
<strong>SSH(Secure Shell)</strong>는 <strong>네트워크로 연결된 다른 컴퓨터에 접속해서 명령어를 실행하는 방법</strong>이다. 주고받는 내용이 <strong>암호화</strong>되기 때문에 비밀번호나 명령어가 네트워크에서 그대로 보이지 않는다. 서버는 대부분 모니터 없이 이 방식으로 관리한다.

SSH는 서버 쪽 프로그램과 접속하는 쪽 프로그램으로 나뉜다. ubuntu-lab에는 설치할 때 OpenSSH server를 설치했고, 맥에는 `ssh` 명령이 기본으로 들어 있다. 서버는 기본으로<strong> 22번 포트</strong>에서 접속을 기다린다. 

<strong>로그인 방식</strong>은 <strong>비밀번호를 입력하는 방식과 키 한 쌍을 쓰는 방식 두 가지</strong>다. 이번에는 처음에 비밀번호로 접속하고, 이후 키 방식으로 바꿨다.

## 비밀번호로 SSH 접속

터미널에서 아래 명령으로 접속할 수 있다.

```bash
ssh 사용자이름@서버IP
```

처음 접속하면 이 서버가 맞는지 확인하는 질문이 나온다. 처음 접속하니 이 서버가 맞는지 확인하는 질문이 나왔다. `yes`를 입력하고 비밀번호를 입력하면 `ubuntu-lab`으로 접속된다.

SSH는 양쪽 신원을 모두 확인한다. 접속하는 쪽이 서버를 확인하는 것이 방금 나온 질문이고, 서버가 접속하는 사람을 확인하는 것이 비밀번호 입력이다. 뒤에서는 이 비밀번호를 사용자 키로 바꾼다.

## SSH 키로 SSH 접속
### SSH 키 만들기

비밀번호는 추측하거나 무작위로 대입해서 뚫릴 수 있다. 그래서 비밀번호 대신 SSH 키로 로그인하도록 바꾸기로 했다.

키 인증은 키 한 쌍을 쓴다. 개인키는 맥에만 두고, 공개키만 서버에 등록한다. 서버는 공개키에 맞는 개인키를 가진 쪽만 들여보낸다.

개인키만으로 어떻게 확인하느냐하면 핵심은 서명이다.

두 키는 짝으로 만들어져서, 개인키로 만든 서명은 짝인 공개키로만 확인할 수 있다. 반대로 공개키만으로는 개인키를 알아낼 수 없다. 그래서 공개키는 서버에 두어도 안전하다.

로그인할 때는 아래 순서로 진행된다. 맥이 "이 공개키로 로그인하겠다"고 서버에 알리면, 서버가 그 공개키가 `~/.ssh/authorized_keys`에 등록돼 있는지 본다. 등록돼 있으면 맥이 이번 접속에서만 쓰는 값(접속마다 달라지는 세션 식별값)에 개인키로 서명해서 보낸다. 서버는 등록된 공개키로 그 서명이 맞는지 확인한다.

서명하는 값은 접속마다 달라서, 이전 접속의 서명을 가로채도 다시 쓸 수 없다.

#### 먼저 기본키가 있는지 확인

```bash
ls ~/.ssh
```

- `~/.ssh`는 SSH 관련 파일이 모이는 맥의 폴더
- `agent`: 키 암호를 기억해 주는 SSH 도우미 프로그램(ssh-agent)이 쓰는 폴더
- `known_hosts`: 지금까지 접속해 본 서버들의 지문 목록 아까 `yes`를 입력했을 때 서버 지문이 여기에 저장
- `known_hosts.old`: `known_hosts`를 고치기 직전에 만들어지는 백업본
#### 키 생성

```bash
ssh-keygen -t ed25519 -C "ubuntu-lab"
```

- `ssh-keygen`은 키 쌍을 만드는 프로그램이다.
- `-t ed25519`는 키 방식을 지정. ed25519는 타원곡선 암호(ECC)를 쓰는 방식으로, 키가 짧고 빠르며 현재 권장되는 방식이다.
- `-C "ubuntu-lab"`은 키에 붙이는 꼬리표(주석)로, 나중에 어느 키인지 구별하는 용도다.

실행하면 질문이 두 가지 나온다.

1. 저장 위치: 그냥 엔터를 누르면 기본값 `~/.ssh/id_ed25519`에 저장된다.
2. passphrase: 개인키에 거는 암호. 호스트의 키 파일이 털려도 이 암호가 없으면 사용할 수 없다. 입력해도 하면에 안보이고, 한 번 더 확인한다. 빈칸이면 암호없는 키가 된다. 설정하길 권한다.  passphrase는 맥 안에서 개인키 파일을 여는 데만 쓰이고 서버로 전송되지 않는다.

#### 결과 확인

```bash
ls ~/.ssh
```

- `id_ed25519`(개인키)와 `id_ed25519.pub`(공개키) 두 파일이 보이면 성공이다.

### 공개키를 서버에 복사
- 서버가 내 열쇠를 알아보려면 공개키(자물쇠)가 서버에 등록돼 있어야 한다. 서버의 `~/.ssh/authorized_keys` 파일이 "이 열쇠로 들어오는 건 허용"하는 명단이다. `ssh-copy-id`가 공개키를 거기에 추가해 준다.

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub 사용자이름@서버IP
```

복사할 파일은 개인키가 아니라 `.pub` 쪽이다. 이 명령은 서버의 `~/.ssh/authorized_keys`에 공개키를 추가한다. 여기서 사용자 이름은 VM 서버의 사용자 이름을 입력해야한다.
이번에는 아직 키 인증이 안 되어 있으니 VM 비밀번호를 한 번 입력한다.
성공하면 `Number of key(s) added: 1`이 나온다.

### 키로 접속되는지 확인

다음 단계에서 비밀번호 로그인을 끌 건데, 키가 안 되는 상태에서 끄면 서버에 못 들어가게 된다. 그래서 끄기 전에 키로 들어가지는지 먼저 확인한다.

접속해 둔 창은 그대로 두고, 맥에서 **새 터미널 탭**을 열어 입력한다.

```bash
ssh -o PasswordAuthentication=no 사용자이름@서버IP
```
- `-o PasswordAuthentication=no`는 이번 접속에서만 비밀번호 방식을 쓰지 않겠다는 옵션이다.
	- `-o`는 **option**의 약자로, SSH 설정 항목을 명령어에서 직접 지정하는 옵션
- 이 옵션을 켠 상태로 접속이 되면 키로 들어온 것이 확실하다. 비밀번호로 들어와서 성공한 것처럼 보이는 경우를 걸러낸다.
- 키에 passphrase를 정했다면 여기서 그 암호를 묻는다. 서버 비밀번호와는 다른 암호다.
- `Permission denied (publickey)`가 나오면 키 등록이 안 된 것이다. 이 경우 비밀번호 로그인을 끄면 안 된다.
- 비밀번호 방식을 끈 상태로 접속이 된다면, 키로 로그인된 것이다.
### 서버에서 지금 적용 중인 SSH 설정 확인
Ubuntu 24.04는 SSH 설정이 `/etc/ssh/sshd_config` 한 파일이 아니라 `/etc/ssh/sshd_config.d/` 폴더의 파일들에도 나뉘어 있다. 

이 폴더의 파일이 메인 파일보다 먼저 읽히고, 같은 항목이 겹치면 먼저 읽힌 값이 이긴다. 메인 파일만 고쳤는데 폴더 안 파일이 `PasswordAuthentication yes`를 쥐고 있으면 설정이 안 먹을 수 있다. 그래서 고치기 전에 현재 상태부터 본다.

```bash
sudo sshd -T | grep -E 'passwordauthentication|pubkeyauthentication'

[sudo] password for 사용자 이름: 

**pubkeyauthentication** yes

**passwordauthentication** yes
```
- `sudo`는 관리자 권한으로 실행한다는 뜻이다. 비밀번호를 물으면 VM 계정 비밀번호를 입력한다.
- `sshd -T`는 SSH 서버가 지금 실제로 적용하는 최종 설정을 전부 출력한다. 파일에 뭐라고 적혀 있든 실제 적용값을 볼 수 있다.
- `grep -E '...'`는 그 출력에서 두 줄만 골라 보여준다.
- 지금은 `passwordauthentication yes`와 `pubkeyauthentication yes`가 나오는 게 정상이다.

```bash
ls /etc/ssh/sshd_config.d/

50-cloud-init.conf
```
설정 조각 파일이 어떤 게 있는지 목록을 본다. `50-cloud-init.conf` 같은 파일이 있으면 그 파일이 `PasswordAuthentication`을 따로 정해 둔 것일 수 있다.
