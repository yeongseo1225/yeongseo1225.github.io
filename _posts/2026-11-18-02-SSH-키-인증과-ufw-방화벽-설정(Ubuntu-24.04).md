이번에는 맥에서 SSH로 서버에 접속하고, 비밀번호 대신 SSH 키로 로그인하도록 바꾼 뒤 ufw 방화벽까지 켜 보았다.

ubuntu-lab은 UTM 공유 네트워크 안에 있어서 실제로는 내 맥에서만 닿는 서버다. 그래도 인터넷에 열린 실제 서버라면 비밀번호만 알면 누구든 접속을 시도할 수 있고, 방화벽도 따로 없는 상태다. 그 상황을 가정하고 연습했다.

## SSH란

<strong>SSH(Secure Shell)</strong>는 <strong>네트워크로 연결된 다른 컴퓨터에 접속해서 명령어를 실행하는 방법</strong>이다. 주고받는 내용이 <strong>암호화</strong>되기 때문에 비밀번호나 명령어가 네트워크에서 그대로 보이지 않는다. 서버는 대부분 모니터 없이 이 방식으로 관리한다.

SSH는 서버 쪽 프로그램과 접속하는 쪽 프로그램으로 나뉜다. ubuntu-lab에는 설치할 때 OpenSSH server를 설치했고, 맥에는 `ssh` 명령이 기본으로 들어 있다. 서버는 기본으로<strong> 22번 포트</strong>에서 접속을 기다린다.

<strong>로그인 방식</strong>은 <strong>비밀번호를 입력하는 방식과 키 한 쌍을 쓰는 방식 두 가지</strong>다. 이번에는 처음에 비밀번호로 접속하고, 이후 키 방식으로 바꿨다.

## 비밀번호로 접속

터미널에서 아래 명령으로 접속할 수 있다.

```bash
ssh 사용자이름@서버IP
```

처음 접속하니 이 서버가 맞는지 확인하는 질문이 나왔다. `yes`를 입력하고 비밀번호를 입력하니 `ubuntu-lab`으로 접속되었다. `yes`를 입력하면 서버의 공개키가 맥의 `~/.ssh/known_hosts`에 저장되고, 다음 접속부터는 서버가 보내는 키와 저장된 키를 비교한다.

SSH는 양쪽 신원을 모두 확인한다. 접속하는 쪽이 서버를 확인하는 것이 방금 나온 질문이고, 서버가 접속하는 사람을 확인하는 것이 비밀번호 입력이다. 뒤에서는 이 비밀번호를 사용자 키로 바꾼다.

## SSH 키로 접속

### SSH 키 만들기

비밀번호는 추측하거나 무작위로 대입해서 뚫릴 수 있다. 그래서 비밀번호 대신 SSH 키로 로그인하도록 바꾸기로 했다.

키 인증은 키 한 쌍을 쓴다. 개인키는 맥에만 두고, 공개키만 서버에 등록한다. 서버는 공개키에 맞는 개인키를 가진 쪽만 들여보낸다.

개인키를 서버에 보내지 않는데 서버가 어떻게 확인하는가? 핵심은 서명이다.

두 키는 짝으로 만들어져서, 개인키로 만든 서명은 짝인 공개키로만 확인할 수 있다. 반대로 공개키만으로는 개인키를 알아낼 수 없다. 그래서 공개키는 서버에 두어도 안전하다.

로그인할 때는 다음과 같이 진행된다. 맥이 "이 공개키로 로그인하겠다"고 서버에 알리면, 서버가 그 공개키가 `~/.ssh/authorized_keys`에 등록돼 있는지 본다. 등록돼 있으면 맥이 이번 접속에서만 쓰는 값(접속마다 달라지는 세션 식별값)에 개인키로 서명해서 보낸다. 서버는 등록된 공개키로 그 서명이 맞는지 확인한다.

서명하는 값은 접속마다 달라서, 이전 접속의 서명을 가로채도 다시 쓸 수 없다.

#### 먼저 기존 키가 있는지 확인

```bash
ls ~/.ssh
```

결과는 `agent`, `known_hosts`, `known_hosts.old` 세 개였고, 키 파일은 없었다.

- `~/.ssh`는 SSH 관련 파일이 모이는 맥의 폴더
- `agent`: 키 암호를 기억해 주는 SSH 도우미 프로그램(ssh-agent)이 쓰는 폴더
- `known_hosts`: 지금까지 접속해 본 서버들의 공개키 목록. 앞에서 `yes`를 입력했을 때 서버의 공개키가 여기에 저장된다.
- `known_hosts.old`: `known_hosts`를 고치기 직전에 만들어지는 백업본

#### 키 생성

```bash
ssh-keygen -t ed25519 -C "ubuntu-lab"
```

- `ssh-keygen`은 키 쌍을 만드는 프로그램이다.
- `-t ed25519`는 키 방식을 지정한다. ed25519는 타원곡선 암호(ECC)를 쓰는 방식으로, 키가 짧고 빠르며 현재 권장되는 방식이다.
- `-C "ubuntu-lab"`은 키에 붙이는 꼬리표(주석)로, 나중에 어느 키인지 구별하는 용도다.

실행하면 질문이 두 가지 나온다.

1. 저장 위치: 그냥 엔터를 누르면 기본값 `~/.ssh/id_ed25519`에 저장된다.
2. passphrase: 개인키 파일에 거는 암호다. 맥에서 개인키 파일이 유출돼도 이 암호가 없으면 사용할 수 없다. 입력해도 화면에 안 보이고, 한 번 더 확인한다. 빈칸이면 암호 없는 키가 된다. 설정하길 권한다. passphrase는 맥 안에서 개인키 파일을 여는 데만 쓰이고 서버로 전송되지 않는다.

#### 결과 확인

```bash
ls ~/.ssh
```

- `id_ed25519`(개인키)와 `id_ed25519.pub`(공개키) 두 파일이 보이면 성공이다.

### 공개키를 서버에 복사

서버가 내 열쇠를 알아보려면 공개키(자물쇠)가 서버에 등록돼 있어야 한다. 서버의 `~/.ssh/authorized_keys` 파일이 "이 열쇠로 들어오는 건 허용"하는 명단이다. `ssh-copy-id`가 공개키를 거기에 추가해 준다.

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub 사용자이름@서버IP
```

복사할 파일은 개인키가 아니라 `.pub` 쪽이다. 이 명령은 서버의 `~/.ssh/authorized_keys`에 공개키를 추가한다. 여기서 사용자 이름은 VM 서버의 사용자 이름을 입력해야 한다.

이번에는 아직 키 인증이 안 되어 있으니 VM 비밀번호를 한 번 입력한다. 성공하면 `Number of key(s) added: 1`이 나온다.

### 키로 접속되는지 확인

다음 단계에서 비밀번호 로그인을 끌 건데, 키가 안 되는 상태에서 끄면 서버에 못 들어가게 된다. 그래서 끄기 전에 키로 들어가지는지 먼저 확인한다.

접속해 둔 창은 그대로 두고, 맥에서 **새 터미널 탭**을 열어 입력한다.

```bash
ssh -o PasswordAuthentication=no 사용자이름@서버IP
```

- `-o PasswordAuthentication=no`는 이번 접속에서만 비밀번호 방식을 쓰지 않겠다는 옵션이다.
    - `-o`는 **option**의 약자로, SSH 설정 항목을 명령어에서 직접 지정하는 옵션
- 이 옵션을 켠 상태로 접속이 되면 키로 들어온 것이 확실하다. 비밀번호로 들어와서 성공한 것처럼 보이는 경우를 걸러낸다.
- 키에 passphrase를 정했다면 여기서 그 암호를 묻는다. 서버 비밀번호와는 다른 암호다.
- `Permission denied (publickey)`가 나오면 키 인증이 되지 않은 것이다. 이 경우 비밀번호 로그인을 끄면 안 된다.
- 비밀번호 방식을 끈 상태로 접속이 된다면, 키로 로그인된 것이다.

## 서버의 비밀번호 로그인 끄기

### 현재 적용 중인 SSH 설정 확인

Ubuntu 24.04는 SSH 설정이 `/etc/ssh/sshd_config` 한 파일이 아니라 `/etc/ssh/sshd_config.d/` 폴더의 파일들에도 나뉘어 있다.

이 폴더의 파일이 메인 파일보다 먼저 읽히고, 같은 항목이 겹치면 먼저 읽힌 값이 이긴다. 메인 파일만 고쳤는데 폴더 안 파일이 `PasswordAuthentication yes`를 쥐고 있으면 설정이 안 먹을 수 있다. 그래서 고치기 전에 현재 상태부터 보았다.

```bash
sudo sshd -T | grep -E 'passwordauthentication|pubkeyauthentication'
```

```text
pubkeyauthentication yes
passwordauthentication yes
```

- `sudo`는 관리자 권한으로 실행한다는 뜻이다. 비밀번호를 물으면 VM 계정 비밀번호를 입력한다.
- `sshd -T`는 SSH 서버가 지금 실제로 적용하는 최종 설정을 전부 출력한다. 파일에 뭐라고 적혀 있든 실제 적용값을 볼 수 있다.
- `grep -E '...'`는 그 출력에서 두 줄만 골라 보여준다.
- 지금은 `passwordauthentication yes`와 `pubkeyauthentication yes`가 나왔다.

설정 조각 파일이 어떤 게 있는지 목록도 보았다.

```bash
ls /etc/ssh/sshd_config.d/
```

```text
50-cloud-init.conf
```

`50-cloud-init.conf` 파일이 하나 있었다. `grep`으로 `PasswordAuthentication`이 적힌 곳을 찾아보았다.

```bash
sudo grep -ri passwordauthentication /etc/ssh/sshd_config /etc/ssh/sshd_config.d/
```

`50-cloud-init.conf`에 `PasswordAuthentication yes`가 적혀 있었고, 메인 설정 `sshd_config`에서는 이 항목이 주석 처리되어 있었다. 폴더 안 파일이 먼저 읽히므로 메인 파일을 고쳐도 이 `yes`가 적용된다. cloud-init이 만든 파일은 직접 고치지 않고, 숫자가 더 작아 먼저 읽히는 파일을 새로 만들었다.

### 내 설정 파일 새로 만들기

```bash
echo 'PasswordAuthentication no' | sudo tee /etc/ssh/sshd_config.d/10-disable-password.conf
```

- `echo '...'`는 글자를 출력하고, `| sudo tee 파일`은 그 글자를 관리자 권한으로 파일에 저장한다. `sudo echo ... > 파일`은 저장 단계에 관리자 권한이 안 걸려 실패하기 때문에 이렇게 쓴다.
- `50-cloud-init.conf`를 직접 고치지 않는 이유는 cloud-init이 이 파일을 다시 만들면 내 수정이 사라질 수 있어서다.
- 파일 이름을 `10-`으로 시작하게 한 이유는 이 폴더의 파일이 숫자 순서로 읽히고 먼저 읽힌 값이 이기기 때문이다. `10`이 `50`보다 앞이라 내 설정이 이긴다.

### 문법 검사

```bash
sudo sshd -t
```

- `sshd`(SSH daemon)는 서버에서 접속을 받는 프로그램이다.
- `-t`는 test의 약자로, SSH 서버를 시작하지 않고 설정 파일만 읽어서 오류가 있는지 검사한다.
- **아무 출력이 없으면 정상이다.** 오류가 있는 설정으로 SSH를 다시 시작하면 접속이 안 될 수 있어서, 적용 전에 이 검사를 거친다.

### 적용될 값 미리 보기

```bash
sudo sshd -T | grep passwordauthentication
```

- 파일을 다시 읽어서 최종적으로 적용될 값을 보여준다. `passwordauthentication no`가 나오면 내 설정이 이긴 것이다. `yes`가 나오면 아직 다른 설정이 이기고 있으니 적용하면 안 된다.

결과는 `passwordauthentication no`였다.

### SSH 서비스에 설정 적용

```bash
sudo systemctl reload ssh
```

- `systemctl`은 서비스를 관리하는 명령이다.
- `reload`는 서비스를 껐다 켜지 않고 설정 파일만 다시 읽게 한다. `restart`는 서비스를 껐다 켜는 방식이다.
- 서비스 이름이 `sshd`가 아니라 `ssh`인 것은 Ubuntu에서 그렇게 등록되어 있기 때문이다.
- 성공하면 아무 출력이 없다.

### 새 설정 확인

#### 키 접속 확인

```bash
ssh 사용자이름@서버IP
```

- 아까처럼 접속되면 정상이다. passphrase를 정했다면 그 암호를 묻는다.

#### 비밀번호 접속 확인

```bash
ssh -o PubkeyAuthentication=no 사용자이름@서버IP
```

`-o PubkeyAuthentication=no`는 이번 접속에서 키를 쓰지 않겠다는 옵션이다. 비밀번호로만 시도하는 상황을 일부러 만든다. 비밀번호를 묻지 않고 바로 `Permission denied (publickey).`가 나왔다.

## ufw 방화벽

ufw의 기본 정책은 들어오는 접속은 막고 나가는 접속은 허용하는 것이라서, 규칙 없이 켜면 22번 포트까지 막혀 접속이 끊길 수 있다. 그래서 켜기 전에 허용할 포트부터 등록했다. SSH용 22번을 먼저, 그다음 nginx용 80번이다.

### 현재 상태 확인

```bash
sudo ufw status
```

- 방화벽이 켜져 있는지, 어떤 규칙이 있는지 보여준다.
- `Status: inactive`는 아직 꺼져 있다는 뜻이다.

### SSH(22/tcp), HTTP(80/tcp) 포트 허용

```bash
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
```

- 방화벽이 꺼져 있어서 규칙이 등록만 되고 아직 적용되지는 않는다. `Rules updated`라고 나오면 된다.

### 등록된 규칙 확인

```bash
sudo ufw show added
```

- 지금까지 등록한 규칙 목록을 보여준다. 방화벽을 켜기 전에 22번이 목록에 있는지 눈으로 확인하는 단계다.
- 22번이 없으면 켜는 순간 접속이 끊기니 반드시 있는지 본다.

### 방화벽 켜기

```bash
sudo ufw enable
```

- `Command may disrupt existing ssh connections` 경고가 나온다. SSH 접속이 끊길 수 있다는 일반 경고다. 22번을 허용해 뒀으니 `y`를 입력하고 엔터를 누른다.
- 성공하면 `Firewall is active and enabled on system startup`이 나온다. 서버를 재부팅해도 계속 켜져 있다는 뜻이다.

### 상태 확인

```bash
sudo ufw status verbose
```

- `Status: active`와 `Default: deny (incoming), allow (outgoing)`이 보인다. "들어오는 건 기본 차단, 나가는 건 허용"이라는 뜻이다.
- 아래쪽 규칙 목록에 22/tcp와 80/tcp가 `ALLOW IN`으로 보인다.

## 80번 포트를 막고 접속해 보기

### 80번 규칙 삭제

80번 규칙을 지우고 접속해 보았다.

```bash
sudo ufw delete allow 80/tcp
```

- 등록해 둔 80번 허용 규칙을 지운다. `Rule deleted`가 나온다.

```bash
sudo ufw status
```

- 목록에 22/tcp만 남았는지 확인한다.

### 브라우저와 curl로 접속해 보기

브라우저에서 `http://서버IP`를 새로고침하니 화면이 계속 로딩만 돌았다. `curl -I --max-time 5 http://서버IP`는 5초 뒤 `Connection timed out`으로 끝났다.

ufw의 `deny`는 막은 포트로 온 요청에 거절 응답을 보내지 않고 버리기 때문에, 접속하는 쪽은 응답을 기다리게 된다. 반대로 `ufw reject`로 막으면 거절 응답을 돌려준다.

### 80번 규칙 되돌리기

확인을 다 했으니 `sudo ufw allow 80/tcp`로 80번 포트를 다시 열었다. `ufw status`에 22번과 80번이 다시 보였고, 브라우저에서 nginx 페이지가 다시 떴다.

## 정리

이번 글에서 한 일은 아래와 같다.

- SSH 키(ed25519)를 만들어 공개키를 서버에 등록했다.
